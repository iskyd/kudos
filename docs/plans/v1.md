# KudOS v1 development plan

This plan breaks v1 into small, ordered tasks that a coding agent (Claude Code) can implement one at a time. Each task is sized for a single focused pull request.

- **Behavior** is defined in `docs/SPEC.md` (exported from the "KudOS — Product Spec & Architecture (v1)" doc).
- **Rules** are in `AGENTS.md`. They apply to every task and are not repeated here.
- **This file** says what to build, in what order, and how to know it's done.

---

## How to use this plan

**For the agent, on every task:**

1. Pick the first unchecked task whose dependencies are all checked. Do not start tasks marked 👤 — they need the maintainer.
2. Read `AGENTS.md`, the spec sections the task cites, and any notes in the [decisions log](#decisions-log).
3. Work on a branch named `t<id>-<short-name>` (for example `t2.3-fit-core`).
4. Implement the **Build** items. Stay inside the task's scope; if something outside it is needed, stop and ask.
5. Meet every **Done when** item, then run `just check` until it passes.
6. Tick the task's checkbox in this file in the same PR, and append any decision you made that the spec didn't settle to the decisions log.
7. If the spec is ambiguous or contradicts `AGENTS.md`, stop and ask instead of guessing.

**Suggested prompt:**

> Read AGENTS.md, PLAN.md and the docs/SPEC.md sections cited by task T2.3. Implement T2.3 on a new branch, meet every "Done when" item, run `just check`, tick the task in PLAN.md, and summarize what you did and any decisions you logged.

**Every task's definition of done also includes** the checklist at the end of `AGENTS.md`: tests for every new or changed function, cross-user isolation tests for new repository methods, no hand-edited generated files, and a clean `just check`.

**Legend:** 👤 = maintainer action required · `deps` = tasks that must be done first

## M0 — Foundation

- [x] **T0.1 · Repository scaffold** — deps: none
  - Spec: Architecture › Repository layout
  - Build:
    - `go mod init` (module path `github.com/OWNER/kudos` until the repository exists) and the directory layout from the spec.
    - Pin generators as Go tools: sqlc, oapi-codegen, goose, River CLI, mockgen (`go get -tool ...`).
    - `justfile` with `generate`, `lint`, `test`, `check`, `dev`, `build` recipes as described in `AGENTS.md`.
    - `.golangci.yml`, `.editorconfig`, `.gitignore`, `LICENSE.md`, `README.md`, `AGENTS.md`, `CLAUDE.md`, `docs/SPEC.md`.
    - `cmd/server/main.go`: start an HTTP server, handle SIGTERM with graceful shutdown, serve `GET /healthz`.
  - Done when:
    - `just check` passes on the skeleton.
    - `/healthz` has a handler test.

- [x] **T0.2 · Configuration, logging and encryption** — deps: T0.1
  - Spec: Non-functional requirements › Security, Deployment and operations
  - Build:
    - Config loaded once from environment and validated: `DATABASE_URL`, `ENCRYPTION_KEY_FILE` or `ENCRYPTION_KEY`, `REGISTRATION_ENABLED`, `LISTEN_ADDR`, `DATA_DIR`, `MAP_TILE_URL`, `LOG_LEVEL`. Document each in `deploy/.env.example`.
    - JSON `slog` logger with a redaction helper for secret-bearing types (they must not print their values).
    - `internal/crypto`: AES-256-GCM `Seal`/`Open` with a key-version prefix on ciphertexts, so the key can be rotated later.
  - Done when:
    - Tests cover every invalid-config case and the defaults.
    - Crypto tests cover round trip, tampered ciphertext, wrong key and wrong version.
    - A test proves secret types render as `[redacted]` in logs.

- [x] **T0.3 · Database foundation** — deps: T0.2
  - Spec: Architecture › Technology choices; Sports and data model
  - Build:
    - Embedded goose migrations run on startup. The first migration enables the `timescaledb` extension.
    - `sqlc.yaml` (engine postgresql, pgx/v5, schema from `migrations/`, queries from `internal/store/queries/`) and `internal/store/generate.go`.
    - `internal/testutil`: start TimescaleDB with testcontainers-go once per package, apply migrations, and give each test an isolated database or schema.
  - Done when:
    - One trivial sqlc query is generated and exercised by an integration test.
    - Migrations apply cleanly twice in a row (idempotent startup).

- [x] **T0.4 · Background jobs** — deps: T0.3
  - Spec: Architecture
  - Build:
    - River schema migrations produced with `go tool river migrate-get` into goose files.
    - River client and worker registry wired in `cmd/server`; graceful job shutdown.
    - Helper for enqueueing inside a transaction (`InsertTx`).
  - Done when:
    - An example job has a test using River's test helpers.
    - A test proves a job enqueued in a rolled-back transaction never runs.

- [x] **T0.5 · API foundation** — deps: T0.1
  - Spec: Architecture; `AGENTS.md` invariants 40–41
  - Build:
    - `api/openapi.yaml` skeleton with shared components: problem+json error, cursor pagination parameters and response envelope.
    - oapi-codegen strict server for chi, generated via `go:generate`.
    - Middleware: request ID, structured access logging (no bodies), panic recovery to problem+json.
    - Cursor encode/decode helpers (opaque, tamper-evident).
  - Done when:
    - Tests cover cursor round trip and tampering, error rendering for each error kind, and recovery middleware.

- [x] **T0.6 · Frontend scaffold** — deps: T0.5
  - Spec: Architecture › Technology choices
  - Build:
    - `web/`: Vite, React, TypeScript strict, Tailwind, shadcn initialized with its CLI, dark-first design tokens, React Router, TanStack Query.
    - API client generated from `api/openapi.yaml` (openapi-typescript + openapi-fetch) with `npm run generate`; wired into `just generate`.
    - ESLint, Prettier, Vitest, React Testing Library, MSW, Playwright.
    - App shell: navigation (Dashboard, Activities, Calendar, Plans, Coach, Settings) with empty pages.
    - Go embeds `web/dist` and serves the SPA with history fallback.
  - Done when:
    - `just check` runs frontend lint, typecheck and tests.
    - A Playwright smoke test loads the shell.

- [x] **T0.7 · Dev loop and CI** — deps: T0.4, T0.6
  - Spec: Non-functional requirements › CI
  - Build:
    - `just dev`: TimescaleDB via `deploy/compose.dev.yml`, Go server with live reload, Vite dev server proxying `/api`.
    - GitHub Actions workflow running `just check` on every pull request, with Go and npm caches.
    - Coverage script enforcing the gates in `AGENTS.md` (generated code excluded).
  - Done when:
    - CI passes on a pull request.
    - A deliberately uncovered function makes the coverage gate fail (verified locally, not committed).

**M0 exit check:** a new contributor can clone, run `just dev`, open the empty app, and run `just check`.

## M2 — Ingestion (spec build step 1)

- [ ] **T2.1 · FIT anonymizer and test corpus** 👤 — deps: M1
  - Spec: Data sources › FIT parsing rules
  - Build (agent):
    - `cmd/fitanon`: re-encodes a FIT file with muktihari/fit, translating every position by a fixed offset to a neutral location, keeping shapes, distances and all other data intact, and replacing device serial numbers.
  - Maintainer 👤:
    - Run `fitanon` on the five sample files (half marathon, ripetute brevi, Zwift ride, pool swim, strength) and commit them to `testdata/fit/`.
  - Done when:
    - `fitanon` tests prove positions move, everything else (records, laps, lengths, sets, developer fields) is byte-for-byte equivalent after decoding.
    - The anonymized corpus is committed.

- [ ] **T2.2 · Activity data model** — deps: T2.1
  - Spec: Sports and data model; Data sources › FIT parsing rules
  - Build:
    - Migrations: `activities` (sport, subtype, source, source ID, start in UTC, UTC offset, summary values, RPE, feel, notes, weather, gear, overrides as JSONB, multisport group), `activity_streams` hypertable (typed columns plus JSONB extras, compression after 30 days), `laps` (with workout step index and intensity), `swim_lengths`, `strength_sets`, `recorded_workouts` (name and steps), `activity_thresholds`, `multisport_groups`, `original_files`.
    - Unique key on (user, source, source activity ID).
    - sqlc queries for insert/upsert and reads.
  - Done when:
    - Repository tests, including cross-user isolation, pass for every query.
    - Re-running the upsert with the same data changes nothing.

- [ ] **T2.3 · FIT parsing: core** — deps: T2.2
  - Spec: Data sources › FIT parsing rules (units, cadence, invalid values, local time, durations, unknown messages, virtual activities)
  - Build:
    - `internal/importer/fit`: decode with muktihari/fit and map sessions, laps and records to the internal model for running, cycling (including virtual), hiking and open-water swimming.
    - Sport and subtype mapping; local offset from the file with a fallback hook for later.
  - Done when:
    - Golden-file tests (with `-update`) for the half marathon, intervals and Zwift samples.
    - Unit tests for each rule: doubled running cadence, sentinel filtering, semicircle conversion, invalid Zwift local time triggering the fallback, virtual subtype.
    - `FuzzDecodeActivity` exists and runs in CI for a short duration.

- [ ] **T2.4 · FIT parsing: sport-specific detail** — deps: T2.3
  - Spec: Data sources › FIT parsing rules (pool swims, strength, structured workouts, thresholds, RPE and feel, developer fields, message timestamps)
  - Build:
    - Swim lengths (active/idle, stroke, strokes) and computed SWOLF.
    - Strength sets and exercise names matched by category + exercise number, first element of the name array.
    - Recorded structured workouts: name, steps with raw values interpreted by type, repeats; lap/set step indices.
    - Thresholds from `time_in_zone`; RPE and feel; developer fields resolved by name (Zwift `target_power` mapped).
    - Multisport files split into separate activities linked by a group. No real triathlon sample exists, so build one in tests with the muktihari encoder.
  - Done when:
    - Golden tests for the swim and strength samples.
    - Tests assert: SWOLF values, exercise-name matching not by position, workout step values (2,000 m, 60 s, 4.167–4.348 m/s), thresholds per sample, synthetic triathlon split into legs.

- [ ] **T2.5 · GPX and TCX parsing** — deps: T2.3
  - Spec: Data sources › Manual input
  - Build: parsers mapping GPX (gpxgo) and TCX (small custom parser) to the same internal model.
  - Done when: tests with small synthetic fixtures in `testdata/gpx/` and `testdata/tcx/`, including missing heart rate and missing elevation.

- [ ] **T2.6 · Ingestion service and manual input** — deps: T2.4, T2.5
  - Spec: Data sources › Manual input; Sports and data model › Rules
  - Build:
    - Service taking a parsed activity plus original bytes: gzip the original into `DATA_DIR`, upsert everything in one transaction, enqueue a derived-values job (a no-op worker until T4.3).
    - Deduplication: source activity ID, otherwise start time + sport + device.
    - Endpoints: upload FIT/GPX/TCX (size-limited multipart), create a manual activity.
    - UI: upload dialog and manual activity form.
  - Done when:
    - Tests prove ingesting the same file twice yields one activity, originals are written and readable, and a failure rolls back the database and the file.
    - Isolation tests for every new query; component tests for both forms.

- [ ] **T2.7 · Daily health data model** — deps: T2.2
  - Spec: Health, wellness and nutrition; Sports and data model › Core entities
  - Build: `daily_metrics` hypertable (resting HR, HRV, sleep duration/stages/score, stress, Body Battery, steps, weight, body composition, SpO2, hydration) with upsert-by-day queries.
  - Done when: repository and isolation tests pass; re-upserting a day with revised values replaces them.

- [ ] **T2.8 · Garmin Personal API recorder** 👤 — deps: T2.6, T2.7
  - Spec: Data sources › Garmin Connect sync (Personal API)
  - Build (agent):
    - Read the endpoint paths, parameters and payload shapes from Garmin's Personal API documentation and Garmin's official Apache-2.0 Python client. Never guess endpoints.
    - `cmd/garmin-record`: uses `GARMIN_PERSONAL_API_KEY` to call every endpoint KudOS needs over a small date range and saves responses to `testdata/garmin/`, with personal identifiers and coordinates redacted.
  - Maintainer 👤:
    - Run the recorder against your account and commit the fixtures.
    - Confirm the activity download ZIP matches the sample format (closes the spec's open question). Note any observed rate-limit behavior in the decisions log.
  - Done when: recorder tests run against an `httptest` server; fixtures committed.

- [ ] **T2.9 · Garmin Personal API client** — deps: T2.8
  - Spec: Data sources › Garmin Connect sync (Personal API); `AGENTS.md` invariants 25–29
  - Build:
    - `internal/connectors/garmin` implementing the `Connector` interface: key → 24-hour token, token cache, typed endpoint methods, sequential requests with exponential backoff and jitter.
    - Typed errors: key rejected, rate limited, upstream error. A 401 re-mints the token once.
  - Done when:
    - Replay tests against the recorded fixtures pass, including 401 → re-mint → success, 401 twice → key rejected, 429 → backoff, malformed payload → error.
    - No test performs a live call.

- [ ] **T2.10 · Garmin connection settings** — deps: T2.9
  - Spec: Data sources › Garmin Connect sync (Personal API) (access, key expiry, schedule)
  - Build:
    - `garmin_connections` table: encrypted key, encrypted cached token, key expiry, status, sync interval, cursor.
    - Endpoints: set key (write-only), status (expiry, last sync, state), set interval (1–24 hours), disconnect.
    - UI: Settings → Garmin with key input, expiry date and warnings.
  - Done when:
    - Tests prove the key is never returned by any endpoint and is stored encrypted.
    - Component tests cover the expiry warning (7 days) and rejected-key states.

- [ ] **T2.11 · Onboarding backfill** — deps: T2.10
  - Spec: Data sources › Onboarding backfill (Personal API)
  - Build:
    - Window selection: 120 days default, 365 maximum.
    - River jobs: list activities, download and ingest each one, fetch health metrics per day. Resumable cursor; pause on rate limit, rejected key or restart.
    - Local-offset fallback using Garmin activity metadata, then the user's timezone.
    - Per-activity failures recorded with the reason and retryable.
    - Progress endpoint; UI progress bar and failure list with retry.
  - Done when:
    - Tests with a fake connector cover: full run, interruption and resume without duplicates, rate-limit pause, a failing activity not blocking others, retry success.

- [ ] **T2.12 · Ongoing sync** — deps: T2.11
  - Spec: Data sources › Garmin Connect sync (schedule, cursor, failure handling)
  - Build:
    - Periodic River job per user at their interval; "Sync now" endpoint and button.
    - Cursor continues from the end of the backfill; each run re-fetches a 48-hour lookback.
    - Status banners: paused, key expiring, key rejected, last error.
  - Done when:
    - Tests cover lookback upserts (revised sleep/HRV replaces old values), Sync now while a sync is running (no duplicate run), and pause on key rejection.

**M2 exit check 👤:** connect a real Garmin account, backfill 120 days, let hourly sync run for a day, and upload one FIT file manually. Log observed rate limits and any parsing failures in the decisions log.

- [ ] **T3.4 · Annotations** — deps: T3.3

- [ ] **T3.5 · Gear** — deps: T3.3

  - Build: gear CRUD, assignment to activities, cumulative distance and time computed on demand, replacement threshold with a warning.

## M4 — Analytics (spec build step 3)

- [ ] **T4.1 · Zone models and versions** — deps: M3
  - Spec: Analytics › Zones
  - Build:
    - `zone_sets` per sport with effective-from dates.
    - Pure functions for each model: Friel running HR and pace, Coggan 7 power zones plus cycling HR, CSS swim pace, % of heart rate reserve fallback.
    - Endpoints and a zones settings page to view and add versions.
  - Done when: boundary tests against published model tables; tests that an activity resolves the version valid on its date.

- [ ] **T4.2 · Zone history from FIT thresholds** — deps: T4.1
  - Spec: Analytics › Zones (zone history from FIT files)
  - Build:
    - On ingest, compare an activity's thresholds with the current version for that sport and create a dated suggestion when they differ.
    - Suggestions UI: confirm or dismiss. A running FTP is never applied to cycling.
  - Done when: tests on the corpus produce the three versions in the spec (lactate threshold HR 176 → 177 → 171, max HR 194 → 195 → 187) and never touch cycling zones from running power.

- [ ] **T4.3 · Derived values pipeline** — deps: T4.1
  - Spec: Analytics › Computation strategy; `AGENTS.md` invariants 10, 23, 24
  - Build:
    - `activity_derived` table; worker computing values on ingest; invalidation on zone change or edit; "recompute all" job.
    - Time-weighted helpers: averages, time in zones.
  - Done when: tests prove time weighting on the strength sample's irregular sampling, invalidation after a zone change and after an edit, and idempotent recompute.

- [ ] **T4.4 · Training load** — deps: T4.3
  - Spec: Analytics › Training load
  - Build:
    - Per-activity load with the fallback chain (power TSS, pace rTSS, swim TSS, hrTSS, session RPE × duration), recording which method was used.
    - Daily fitness, fatigue and form computed on demand; endpoint.
  - Done when: hand-computed test vectors for each method and for the CTL/ATL/TSB recurrences, including days without training.

- [ ] **T4.5 · Wellness inputs** — deps: M1
  - Spec: Health, wellness and nutrition
  - Build: daily check-in (soreness, sleep quality, stress, motivation, note), body metrics, injury and illness log (free text, start and end dates), optional menstrual cycle tracking; endpoints and UI.
  - Done when: repository, isolation, handler and component tests for each input.

- [ ] **T4.6 · Readiness** — deps: T4.4, T4.5
  - Spec: Analytics › Readiness
  - Build:
    - Baselines (7-day and 60-day), components (HRV, resting HR, sleep, form, check-in), caps for active illness or injury, a visible breakdown.
    - Hidden ("collecting baseline") until 14 days of HRV and resting HR exist. Default weights documented in the decisions log.
    - Endpoint and dashboard-ready widget.
  - Done when: tests cover each component, the caps, the 14-day gate and deterministic output for fixed inputs.

- [ ] **T4.7 · Records and best efforts** — deps: T4.3
  - Spec: Analytics › Records and curves; Sports and data model › Rules
  - Build:
    - Fastest 1K, 5K, 10K, half marathon and marathon as best segments within any run; longest run, ride, swim and hike; best power for standard durations; record history.
    - Virtual distance and elevation excluded. Labels "since <date>" based on the backfill window.
  - Done when: tests on synthetic streams with known answers, plus a test that a virtual ride never sets a distance record.

- [ ] **T4.8 · Curves and threshold estimates** — deps: T4.7
  - Spec: Analytics › Records and curves; Analytics › Zones (suggestions after onboarding)
  - Build: power-duration and pace-duration curves (all time and per period); FTP estimate (95% of best 20-minute power) and threshold pace estimate, feeding the T4.2 suggestion flow.
  - Done when: curve monotonicity and known-answer tests; suggestion created when an estimate changes.

- [ ] **T4.9 · Running and swim analytics** — deps: T4.7
  - Spec: Analytics › Records and curves (running analytics); Sports and data model (swimming)
  - Build:
    - VO2max estimate (document the chosen published method in the decisions log), race predictions, efficiency factor, aerobic decoupling, running dynamics trends.
    - Swim: CSS estimate from best efforts, SWOLF trends.
  - Done when: known-answer tests for each formula with the method cited in code comments.

**M4 exit check:** the half marathon shows correct load, zones and best efforts; readiness appears once 14 days of data exist.

- [ ] **T6.1 · LLM providers and clients** — deps: M5
